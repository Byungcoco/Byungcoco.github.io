## 1. 개요

<Chips items={frontmatter.chips} />

게임 루프는 오브젝트 목록을 순회하며 갱신하는데, 순회 도중에 목록 자체를 바꾸면 반복자가 무효화됩니다. 그래서 생성·삭제처럼 목록을 바꾸는 작업은 요청으로 모아 두었다가 순회가 끝난 뒤 한 번에 처리하고, 객체는 "살아 있음 / 죽는 중 / 삭제 대기" 같은 생명 상태로 지금 할 수 있는 일을 구분합니다.

충돌 허용을 생명 상태에 묶은 뒤로는, 쓰러지는 적이 다시 맞거나 밀리는 문제가 개별 오브젝트 코드를 고치지 않고도 사라졌습니다. 죽음을 판단하는 곳이 여럿이어도 상태는 한 번만 바뀝니다.

## 2. 문제

> 레이어는 오브젝트를 배열로 들고 순회하며 갱신합니다. 공격이 맞는 순간 이펙트를 만들거나 체력이 0이 된 적이 스스로 사라지는 일은 모두 이 순회 도중에 일어나는데, 그 자리에서 배열에 넣고 빼면 순회 중인 컨테이너가 바뀌어 다음 원소를 건너뛰거나 지워진 객체를 건드리게 됩니다. 또 "죽었다"는 상태가 하나뿐이면, 사망 애니메이션을 재생하는 동안에도 계속 맞거나 다른 캐릭터와 부딪혀 밀려납니다. 실제로 쓰러지는 적이 다시 맞거나 플레이어에게 밀리는 문제가 있었고, 풀로 돌아간 객체가 다른 시스템에서는 여전히 살아 있는 것처럼 보였습니다. 생성·삭제·레벨 전환을 순회 밖으로 미루고, 객체가 지금 무엇을 할 수 있는지를 상태 하나로 정리해야 했습니다.

## 3. 구조 요약

바꾸는 시점과 요청하는 시점을 나눴습니다. 게임 코드는 언제든 생성·삭제·레벨 전환을 요청만 하고, 실제 컨테이너 변경은 이벤트 매니저가 순회 밖에서 몰아서 처리합니다. 객체 쪽에서는 생명 상태 하나로 갱신·렌더·충돌 여부가 함께 정해집니다.

생성·삭제·레벨 전환 요청을 종류별 큐에 모았다가 한 번에 처리합니다. 처리 도중(`m_bFlushing`)에 새로 들어온 요청은 보류 큐(`_Pending`)에 따로 쌓습니다.

void CGameInstance::Request_AddObject(_uint iCloneLevelIndex, const wstring& wstrLayerTag, CGameObject* pGo, std::function<void(CGameObject*)> onSpawnedCallback)
{
	if (!pGo)
		return;

	AddEventDesc desc = {};
	desc.iCloneLevelIndex = static_cast<_int>(iCloneLevelIndex);
	desc.wstrLayerTag = wstrLayerTag;
	desc.pClone = pGo;
	if (onSpawnedCallback)
		desc.callback = std::move(onSpawnedCallback);
	m_pEvent_Manager->Push_AddEvent(desc);
}
// ... 코드 중략

void CGameInstance::Request_DeleteGameObject(_uint iCloneLevelIndex, CGameObject* pGo)
{
	if (!pGo)
		return;

	RemoveEventDesc desc = {};
	desc.iClonedLevelIndex = iCloneLevelIndex;
	desc.pGo = pGo;
	m_pEvent_Manager->Push_RemoveEvent(desc);
}
```

</Editor>

게임 코드는 `Request_AddObject` / `Request_DeleteGameObject`로 요청만 합니다. 생성 요청에는 콜백을 함께 넘길 수 있어서, "레이어에 실제로 들어간 뒤에 할 일"(위치 지정, 대상 연결 등)을 요청한 쪽이 미리 정해 둘 수 있습니다. 객체를 바로 받아 쓰지 않고 콜백으로 받기 때문에, 아직 레이어에 없는 객체를 다른 시스템이 건드릴 일이 없습니다.

#### B. 보류 큐와 생성·삭제 상쇄

void CEvent_Manager::Push_AddEvent(const AddEventDesc& desc)
{
	if (m_bFlushing == false)
		m_queAddGameObject.push(desc);
	else
		m_queAddGameObject_Pending.push(desc);
}

void CEvent_Manager::Push_RemoveEvent(const RemoveEventDesc& desc)
{
	if (desc.pGo == nullptr)
		return;

	if (Cancel_AddQueued(desc.pGo))
		return;

	Safe_AddRef(desc.pGo);
	if (m_bFlushing == false)
		m_queRemoveGameObject.push(desc);
	else
		m_queRemoveGameObject_Pending.push(desc);
}
```

<Editor file="Event_Manager.cpp" fn="Cancel_AddQueued(...)">

```cpp
_bool CEvent_Manager::Cancel_AddQueued(CGameObject* pGo)
{
	_bool bCancelled{ false };

	{
		std::queue<AddEventDesc> tmp;
		while (m_queAddGameObject.empty() == false)
		{
			AddEventDesc desc = m_queAddGameObject.front();
			m_queAddGameObject.pop();
			if (desc.pClone == pGo)
			{
				Clear_AddEvent(desc);
				bCancelled = true;
			}
			else
				tmp.push(desc);
		}
		m_queAddGameObject.swap(tmp);
	}
	{
		std::queue<AddEventDesc> tmp;
		while (m_queAddGameObject_Pending.empty() == false)
		{
			AddEventDesc desc = m_queAddGameObject_Pending.front();
			m_queAddGameObject_Pending.pop();
			if (desc.pClone == pGo)
			{
				Clear_AddEvent(desc);
				bCancelled = true;
			}
			else
				tmp.push(desc);
		}
		m_queAddGameObject_Pending.swap(tmp);
	}

	return bCancelled;
}
```

</Editor>

처리 중(`m_bFlushing`)에 들어온 요청은 보류 큐로 보내, 지금 비우고 있는 큐가 처리 도중 늘어나지 않게 합니다. 삭제 요청이 들어오면 먼저 같은 객체의 생성 요청이 아직 큐에 남아 있는지 찾습니다. 있으면 생성 요청을 지우고 삭제 요청도 넣지 않으므로, 한 프레임 안에 만들어졌다 사라지는 객체는 레이어에 한 번도 들어가지 않습니다. 삭제 요청을 넣을 때는 참조 카운트를 하나 올려, 처리되기 전에 다른 곳에서 해제되더라도 큐가 해제된 객체를 가리키지 않게 했습니다.

#### C. 처리 순서와 레벨 전환

<Editor file="Event_Manager.cpp" fn="Flush_All()">

```cpp
void CEvent_Manager::Flush_All()
{
	m_bFlushing = true;

	const _bool bHasLevelChange = !m_queChangeLevel.empty() || !m_queChangeLevel_Pending.empty();

	if (bHasLevelChange)
	{
		// 삭제는 처리
		Flush(EventType::OBJECT_REMOVE);
		Flush_Pending(EventType::OBJECT_REMOVE);

		_bool bShouldChange = { false };
		ChangeLevelEventDesc shouldLevelChangeDesc = {};

		// 이번프레임에 들어온것 중 후처리 우선
		if (m_queChangeLevel_Pending.empty() == false)
		{
			shouldLevelChangeDesc = m_queChangeLevel_Pending.back();
			m_queChangeLevel_Pending.pop();
			bShouldChange = true;
		}
		else if (m_queChangeLevel.empty() == false)
		{
			shouldLevelChangeDesc = m_queChangeLevel.back();
			m_queChangeLevel.pop();
			bShouldChange = true;
		}


		// 나머지 필요없으니 폐기
		Clear_All();
		m_bFlushing = false;

		if (bShouldChange)
			Change_Level(shouldLevelChangeDesc);

		return;
	}
	else
	{
		// Delete 우선
		Flush(EventType::OBJECT_REMOVE);
		Flush(EventType::OBJECT_ADD);
	}

	m_bFlushing = false;

	// Delete 우선
	Flush_Pending(EventType::OBJECT_REMOVE);
	Flush_Pending(EventType::OBJECT_ADD);
}
```

</Editor>

평소에는 삭제를 먼저, 생성을 나중에 처리합니다(<FigRef n={2} />). 같은 프레임에 삭제와 생성이 함께 들어와도 정리를 먼저 끝낸 레이어에 새 객체가 들어갑니다.

<Fig n={3} white max={560} src="/img/reviews/duet/06-lifecycle/level.png" caption="레벨 전환 요청이 있으면 삭제만 처리하고 나머지 요청은 폐기" />

레벨 전환 요청이 있으면 삭제만 마무리하고, 생성 요청은 모두 버린 뒤 레벨을 바꿉니다(<FigRef n={3} />). 버그를 겪고 나서 넣은 규칙이 아니라, 설계할 때 "곧 사라질 레벨에 쌓인 생성 요청은 새 레벨에서 의미가 없다"고 판단해 정한 순서입니다. 삭제할 객체가 풀에서 나온 것이면 지우지 않고 풀로 돌려보내므로, 게임 코드는 객체가 풀 소속인지 몰라도 같은 함수로 삭제를 요청할 수 있습니다.

#### A. 두 단계 죽음

enum class ELifeState : _ushort
{
	Alive = 0,
	Dying,
	Pending,
	Pooled,
};
	// ... 코드 중략
	enum EFlag : _uint
	{
		NONE = 0,
		ACTIVE = 1 << 0,
		RENDER = 1 << 1,
		COLLIDE = 1 << 2,
		//=================================//
		DEFAULT = ACTIVE | RENDER | COLLIDE,
		ALL = 0xFFFFFFFF,
	};

void CGameObject::Set_Dead(_bool bIsStatic)
{
    if (m_eState == ELifeState::Pending || m_eState == ELifeState::Pooled)
        return;

    m_eState = ELifeState::Pending;
    Clamp_FlagsByState();

}

void CGameObject::Set_Dying()

    m_eState = ELifeState::Dying;

}

<Editor file="GameObject.cpp" fn="Clamp_FlagsByState()">

```cpp
void CGameObject::Clamp_FlagsByState()
{
    if (m_eState == ELifeState::Pending || m_eState == ELifeState::Pooled)
    {
        m_iObjectFlags = NONE;
    }
    else if (m_eState == ELifeState::Dying)
    {
        m_iObjectFlags = ACTIVE | RENDER;
    }
    else
    {
        m_iObjectFlags = DEFAULT;
    }
}
```

</Editor>

<Fig n={4} white max={620} src="/img/reviews/duet/06-lifecycle/state.png" caption="Alive → Dying → Pending / Pooled 상태와 상태별로 허용되는 동작" />

죽음을 두 단계로 나눴습니다(<FigRef n={4} />). `Set_Dying`은 사망 애니메이션을 재생하는 단계로, 갱신과 렌더는 계속하되 충돌은 끕니다. 쓰러지는 동안 다시 맞거나 공격을 맞히지 않고, 다른 캐릭터와 부딪혀 밀리지도 않습니다. 연출이 끝나면 `Set_Dead`가 상태를 Pending으로 바꾸고 모든 플래그를 끈 뒤 삭제를 요청합니다. 실제 삭제는 다음 프레임에 일어나지만 상태는 즉시 바뀌므로, 같은 프레임의 다른 시스템도 이 객체를 죽은 것으로 봅니다. 이미 Pending이거나 풀에 들어간 객체는 다시 요청하지 않아서, 여러 곳에서 동시에 죽음을 판정해도 삭제 요청은 한 번만 들어갑니다.

void CGameObject::Set_Active(_bool bActive)
{
    if (bActive && (m_eState == ELifeState::Pending || m_eState == ELifeState::Pooled))
        return;

    bActive 
        ? Engine_Utils::Add_Flag(m_iObjectFlags, ACTIVE)
        : Engine_Utils::RemoveHard_Flag(m_iObjectFlags, ACTIVE);
}

// Pending, Pooled는 Default Flag
void CGameObject::Set_Render(_bool bRender)
{
    if (bRender && (m_eState == ELifeState::Pending || m_eState == ELifeState::Pooled))
        return;

    bRender 
        ? Engine_Utils::Add_Flag(m_iObjectFlags, RENDER)
        : Engine_Utils::RemoveHard_Flag(m_iObjectFlags, RENDER);
}

// Pending, Pooled는 Default Flag
void CGameObject::Set_CollideEnabled(_bool bCollide)
{
    if (bCollide && (m_eState != ELifeState::Alive))
        return;

    bCollide
        ? Engine_Utils::Add_Flag(m_iObjectFlags, COLLIDE)
        : Engine_Utils::RemoveHard_Flag(m_iObjectFlags, COLLIDE);
}

게임 코드가 개별 플래그를 켜더라도 상태가 허용하지 않으면 켜지지 않습니다. 삭제 대기 중인 객체의 렌더를 실수로 다시 켜는 일도 이렇게 막힙니다. 풀에서 꺼낼 때는 상태를 Alive로 되돌리고 `Awake`를 다시 받도록 표시를 지워, 재사용된 객체도 처음 만들어진 객체와 같은 초기화 순서를 거칩니다.

## 5. 피드백

**버려지는 요청을 요청한 쪽이 알 수 없습니다.** 레벨 전환 때 생성 요청을 버리는 규칙 자체는 의도한 것이지만, 버려진 요청의 콜백은 호출되지 않습니다. 콜백에서 대상을 연결하려던 쪽은 실패를 모른 채 기다리게 됩니다. 콜백에 성공 여부를 함께 넘기는 편이 안전합니다.

남은 개선점입니다.

- 생성·삭제 상쇄(`Cancel_AddQueued`)는 `std::queue`를 통째로 다시 만들어 비용이 큽니다. 한 프레임에 만들었다 지우는 경우가 거의 없어 실제로 드러나지는 않았지만, 객체에 "생성 대기 중" 표시를 두면 큐를 뒤지지 않아도 됩니다.
- `Is_Active`·`Can_Render`는 플래그만 확인합니다. 플래그를 직접 바꾸는 코드가 생기면 상태와 어긋날 수 있습니다.
- 생명 상태와 풀 소속 여부가 따로 관리되어, 잘못된 조합이 생길 수 있습니다.
