## 1. 개요

<Chips items={frontmatter.chips} />

데이터 기반 AI는 "어떤 조건에서 어떤 행동으로 넘어가는가"를 코드가 아니라 데이터 파일에 적습니다. 코드는 거리 판정이나 이동 같은 재료 함수만 이름으로 제공하고, 상태 전이 규칙은 데이터에서 그 이름들을 조합해 만듭니다. 패턴을 바꿀 때 다시 빌드할 필요가 없고, 같은 코드로 여러 몬스터를 만들 수 있습니다.

판단 재료는 코드에, 조합은 데이터에 두었기 때문에 일반 몬스터와 보스가 같은 상태 클래스를 쓰고, 패턴 확률·쿨타임·전이는 빌드 없이 바꿀 수 있습니다.

## 2. 문제

> 나루토 모작에서는 입력 인터페이스를 나눠 적과 플레이어가 같은 상태 클래스를 쓰게 했지만, 적의 "판단"(언제 공격하고, 언제 거리를 벌리는가)은 여전히 C++ 코드 안에 있었습니다. 행동 하나를 바꾸려 해도 상태 클래스를 고치고 다시 빌드해야 했습니다. 최종 프로젝트에는 일반 몬스터와 패턴이 많은 보스가 함께 있었습니다. 몬스터 종류만큼 상태 클래스를 만들면 "거리 안이면 공격, 맞으면 경직, 쿨타임이 끝난 패턴 중 하나를 고른다"는 같은 규칙이 클래스마다 되풀이됩니다. 규칙의 재료(조건과 동작)는 코드로 한 번만 만들고, 그 조합은 데이터로 바꿀 수 있어야 했습니다.

## 3. 구조 요약

판단 재료와 판단 규칙을 나눴습니다. 거리·방향·피격 종류 같은 판단 재료는 컨트롤 컨텍스트가 계산하고, 이를 묻는 조건·동작 함수는 팩토리에 이름으로 한 번 등록합니다. 어떤 상태에서 어떤 조건으로 어디로 넘어갈지는 몬스터별 JSON이 정합니다.

```cpp
inline void from_json(const json& j, STATE_TRANSITION& d)
{
	if (j.contains("vecConditionEntry"))
	{
		j.at("vecConditionEntry").get_to(d.vecConditionEntry);
	}
	else if (j.contains("vecCondition"))
	{
		auto vec = j.at("vecCondition").get<vector<string>>();
		for (auto& str : vec)
		{
			CONDITION_ENTRY entry{};
			entry.strCondition = str;
			d.vecConditionEntry.push_back(entry);
		}
	}
	j.at("mapRandomStatePool").get_to(d.mapRandomStatePool);
}
```

조건과 기능은 대부분 한 줄짜리 람다입니다. 실제 계산은 컨트롤 컨텍스트에 있고, 팩토리는 "이 이름이면 이 질문을 한다"는 연결만 맡습니다. 시그니처는 매크로로 고정해, 람다마다 인자 형식이 달라지지 않게 했습니다. 인자가 필요한 조건은 이름에 `param_`을 붙이고 JSON의 `tParam`에서 값을 꺼내 씁니다. 같은 이름을 두 번 등록하면 초기화가 실패하므로, 오타로 함수가 덮이는 실수는 시작 시점에 잡힙니다.

```cpp
HRESULT CStateBase_Monster::Bind_Transition(vector<DTO::STATE_TRANSITION>& transition)
{
	auto factory = CMonsterState_Factory::GetInstance();

	for (auto& trans : transition)
	{
		trans.vecConditionIdx.clear();
		trans.mapRandomStatePoolIdx.clear();
		trans.fTotalWeight = 0.f;

		// CONDITION_ENTRY 순회 런타임 바인딩
		for (auto& entry : trans.vecConditionEntry)
		{
			auto func = factory->GetCondition(entry.strCondition);
			if (func == nullptr)
				return E_FAIL;

			_uint idx = (_uint)m_vecCondition.size();

			BOUND_CONDITION bound{};
			bound.func = std::bind(func, this, std::placeholders::_1);
			bound.tParam = entry.tParam;

			m_vecCondition.push_back(bound);
			trans.vecConditionIdx.push_back(idx);
		}

		// 전이 상태 id 매핑
		for (auto& value : trans.mapRandomStatePool)
		{
			trans.fTotalWeight += value.second;

			auto itr = m_umapState.find(value.first);
			if (itr == m_umapState.end())
				return E_FAIL;
			_int stateIdx = itr->second;
			trans.mapRandomStatePoolIdx.emplace(stateIdx, value.second);
		}
	}

	return S_OK;
}
```

```cpp
HRESULT CStateBase_Monster::Bind_StartConditionFeature()
{
	auto factory = CMonsterState_Factory::GetInstance();
	// ... 코드 중략
	for (auto& conditionfeature : m_pDesc->vecStartConditionFeature)
	{
		// feature는 필수
		auto featFunc = factory->GetFeature(conditionfeature.feat.strFeature);
		if (!featFunc)
			return E_FAIL;

		// cond는 비면 always로 치환
		string condName = conditionfeature.cond.strCondition.empty()
			? "condition_true_always"
			: conditionfeature.cond.strCondition;
		auto condFunc = factory->GetCondition(condName);
		if (!condFunc) return E_FAIL;

		BOUND_CONDFEATURE bound{};
		bound.condParam = conditionfeature.cond.tParam;
		bound.featParam = conditionfeature.feat.tParam;

		bound.condition = std::bind(condFunc, this, std::placeholders::_1);
		bound.feature = std::bind(featFunc, this, std::placeholders::_1, std::placeholders::_2);

		m_vecStartConditionFeature.push_back(bound);
	}

}
```

<Fig n={2} white max={820} src="/img/reviews/duet/07-boss-ai/bind.png" caption="JSON의 조건·기능 이름 → 팩토리에서 함수 조회 → 상태에 묶어 두기" />

이름을 함수로 바꾸는 일은 상태가 만들어질 때 한 번만 합니다(<FigRef n={2} />). 팩토리 함수의 첫 인자(상태)는 `std::bind`로 `this`에 고정하고, 인자는 JSON 값을 함께 저장해 둡니다. 다음 상태 이름도 이때 인덱스로 바꿔 두므로, 매 프레임에는 문자열 비교 없이 함수 호출과 인덱스만 남습니다. 등록되지 않은 이름이 있으면 상태 생성이 실패해, 오타가 있는 JSON은 실행 전에 걸러집니다. 시작·종료 기능은 조건을 비워 두면 항상 참인 조건으로 바꾸므로, JSON에 "항상" 조건을 일일이 적지 않아도 됩니다.

```cpp
		return;

		return;

	// 로컬 상태 전이
	if (Check_Transition(m_pDesc->vecStateTransition))
		return;

	// 기능 실행
	for (auto& feat : m_vecFeature)
	{
		if (feat.bIsOnce && feat.bIsExecuted)
			continue;

		feat.func(fTimeDelta, feat.tParam);

		feat.bIsExecuted = true;
	}

	for (auto& conditionfeature : m_vecConditionFeature)
	{
		if (conditionfeature.condition(conditionfeature.condParam))
		{
			if (conditionfeature.bIsOnce && conditionfeature.bIsExecuted)
				continue;

			conditionfeature.feature(fTimeDelta, conditionfeature.featParam);

			conditionfeature.bIsExecuted = true;
		}
	}
}
```

## 5. 피드백

**일부 조건이 검사하면서 상태를 바꿉니다.** `IsHitLight` 같은 피격 조건은 참이면 피격 플래그를 지우고, `IsAttackLanded`도 확인과 동시에 플래그를 지웁니다. 조건은 "묻기만 하는" 함수여야 하는데 소비까지 하므로, 같은 프레임에 두 전이가 같은 조건을 쓰면 먼저 검사한 쪽만 참을 받습니다. 결국 JSON의 전이 순서가 결과를 바꾸게 되어, 데이터만 보고는 동작을 예측하기 어렵습니다. 소비는 상태 시작 기능으로 옮기고 조건은 읽기만 하도록 했어야 합니다.

남은 개선점입니다.

- 잘못된 이름이 있는 JSON은 상태 생성에서 걸러지지만, 어느 상태의 어떤 이름인지는 남지 않습니다. 로드할 때 문제 위치를 출력하거나 툴에서 미리 검사하는 단계가 필요합니다.
- 가중치 합을 정수로 잘라(`rand() % total`) 소수 가중치가 적힌 비율대로 뽑히지 않습니다. 실수 분포를 쓰는 편이 맞습니다.
- 상태마다 이름→인덱스 표를 복사해 들고 있습니다. 상태 컴포넌트의 표를 참조로 공유하면 복사를 줄일 수 있습니다.
