## 1. 개요

<Chips items={frontmatter.chips} />

컴포넌트 패턴은 기능을 상속 대신 독립된 부품으로 만들어 오브젝트에 붙이는 방식입니다. 엔진과 게임 코드가 나뉜 구조에서는 엔진이 미리 아는 부품과 게임이 나중에 만드는 부품을 어떻게 같은 오브젝트에 붙일지도 함께 정해야 합니다.

엔진 컴포넌트와 클라이언트 컴포넌트를 나눈 덕분에 게임 기능을 추가해도 엔진을 고치지 않게 되었고, 엔진 컴포넌트를 조회할 때의 캐스팅도 사라졌습니다.

## 2. 문제

> 카타나 제로 모작의 컴포넌트 조회 함수는 부모 타입 포인터를 돌려줘서, 꺼낼 때마다 호출부에서 다시 캐스팅해야 했습니다. 컴포넌트 갱신도 오브젝트가 하나씩 직접 불러야 했습니다. 이번 엔진은 엔진과 클라이언트가 DLL로 나뉩니다. 트랜스폼·모델·충돌체처럼 엔진이 제공하는 컴포넌트와 달리, 체력·스킬·락온처럼 게임마다 다른 컴포넌트는 엔진이 알 수 없습니다. 모든 컴포넌트를 엔진의 열거형 슬롯에 넣으면 게임 기능을 하나 추가할 때마다 엔진을 고쳐야 했습니다.

## 3. 구조 요약

엔진 컴포넌트와 클라이언트 컴포넌트를 다른 그릇에 담았습니다. 엔진이 아는 컴포넌트는 타입 번호를 인덱스로 쓰는 고정 배열에, 게임 쪽 컴포넌트는 이름을 키로 쓰는 맵에 둡니다. 그래서 엔진은 클라이언트 컴포넌트의 타입을 몰라도 등록·갱신·해제를 할 수 있습니다.

엔진이 제공하는 컴포넌트는 `_ID` 값을 인덱스로 쓰는 고정 배열(`m_Components`)의 칸 하나에 들어갑니다. 카타나 제로 모작의 슬롯 방식을 이어받되, `Get_Component`가 조회 결과를 요청한 타입으로 바로 돌려주고 `Add_Component`는 기존 것을 해제한 뒤 교체합니다.

#### B. 타입 그대로 조회·추가

<Editor file="GameObject.h" fn="CGameObject::Get_Component<T>(), CGameObject::Add_Component<T>(...)">

```cpp
template <typename T>
inline T* CGameObject::Get_Component()
{
	static_assert(T::_ID >= EComponentType::TRANSFORM || T::_ID < EComponentType::END, "ComponentType ID is invalid");
	static_assert(T::_ID != EComponentType::SCRIPT, "Script type components dont support this feature. Please check the function name");
	return static_cast<T*>(m_Components[ENUM_TO_UINT(T::_ID)]);
}

template <typename T>
inline HRESULT CGameObject::Add_Component(_uint iLevelIndex, const wstring& wstrPrototypeTag, void* pArg)
{
	static_assert(T::_ID >= EComponentType::TRANSFORM || T::_ID < EComponentType::END, "ComponentType ID is invalid");
	static_assert(T::_ID != EComponentType::SCRIPT, "Script type components dont support this feature. Please check the function name");

	if (m_Components[ENUM_TO_UINT(T::_ID)])
		Safe_Release(m_Components[ENUM_TO_UINT(T::_ID)]);

	if (!((m_Components[ENUM_TO_UINT(T::_ID)] =
		dynamic_cast<CComponent*>(CGameInstance::GetInstance()->Clone_Prototype(EPrototypeType::COMPONENT, iLevelIndex, wstrPrototypeTag, pArg)))))
		return E_FAIL;

	m_Components[ENUM_TO_UINT(T::_ID)]->Set_Owner(this);
	return S_OK;
}
```

</Editor>

조회 함수가 `static_cast<T*>`까지 맡으므로, 호출하는 쪽은 `Get_Component<CTransform>()`처럼 타입만 적으면 바로 그 타입을 받습니다. 카타나 제로 모작에서 호출부마다 반복하던 캐스팅이 템플릿 안으로 들어간 것입니다. 추가할 때는 프로토타입 태그로 원본을 복제해 칸에 넣고 소유자를 연결하며, 같은 종류가 이미 있으면 해제하고 새것으로 바꿉니다. 스크립트 타입을 넘기면 `static_assert`가 컴파일 단계에서 막아, 두 그릇이 섞이지 않게 했습니다.

클라이언트가 만드는 컴포넌트의 기반입니다. 엔진은 이 기반 타입만 알고, 실제 종류는 `Add_Script_Component`로 등록할 때 붙인 이름(`m_ScriptComponents`의 키)으로 구분합니다. 등록된 스크립트는 `Update_Script_Components`가 모두 갱신합니다.

#### A. 스크립트 기반

#### B. 이름으로 등록·조회

<Editor file="GameObject.cpp" fn="CGameObject::Get_Script_Component(...), CGameObject::Add_Script_Component(...)">

```cpp
inline CMonoBehaviour* CGameObject::Get_Script_Component(const wstring& wstrComponentTag)
{
    unordered_map<wstring, CMonoBehaviour*>::iterator itr = m_ScriptComponents.find(wstrComponentTag);
    if (itr == m_ScriptComponents.end())
        return nullptr;
    else
        return itr->second;
}
// ... 코드 중략

HRESULT CGameObject::Add_Script_Component(const wstring &wstrComponentTag, const wstring& wstrPrototypeTag, void* pArg)
{
    CMonoBehaviour* pComp = { nullptr };
    if ( nullptr == (pComp = dynamic_cast<CMonoBehaviour*>(m_pGameInstance->Clone_Prototype(EPrototypeType::COMPONENT, 0/* STATIC */, wstrPrototypeTag, pArg))))
        return E_FAIL;

    unordered_map<wstring, CMonoBehaviour*>::iterator itr = m_ScriptComponents.find(wstrComponentTag);
    if (itr != m_ScriptComponents.end())
        return E_FAIL;

    m_ScriptComponents.insert(unordered_map<wstring, CMonoBehaviour*>::value_type(wstrComponentTag, pComp));
    pComp->Set_Owner(this);
    return S_OK;
}
```

</Editor>

등록은 엔진 컴포넌트와 같은 프로토타입 복제 경로를 쓰고, 결과를 `CMonoBehaviour*`로 확인한 뒤 이름으로 맵에 넣습니다. 엔진 코드는 `CStatComponent`나 `CLockon` 같은 클라이언트 타입을 한 번도 언급하지 않으므로, 게임 기능을 추가해도 엔진 열거형과 엔진 코드는 바뀌지 않습니다.

#### C. 일괄 갱신과 해제

<Editor file="GameObject.cpp" fn="CGameObject::Update(...), CGameObject::Update_Script_Components(...), CGameObject::Free()">

```cpp
void CGameObject::Update(const _float fTimeDelta)
{
    Update_Script_Components(fTimeDelta);
}
// ... 코드 중략

void CGameObject::Update_Script_Components(const _float fTimeDelta)
{
    for (auto& Pair : m_ScriptComponents)
    {
        if (Pair.second)
            Pair.second->Update(fTimeDelta);
    }
}

void CGameObject::Safe_Release_Component()
{
    for (CComponent*& pElement : m_Components)
    {
        Safe_Release(pElement);
    }
    m_Components.fill(nullptr);
}

void CGameObject::Safe_Release_ScriptComponent()
{
    for (auto itr = m_ScriptComponents.begin();
        itr != m_ScriptComponents.end();
        ++itr)
    {
        if (itr->second)
        {
            CMonoBehaviour* pMono = itr->second;
            Safe_Release(pMono);
        }
    }
    m_ScriptComponents.clear();
}

void CGameObject::Free()
{
    Super::Free();
    Safe_Release_Component();
    Safe_Release_ScriptComponent();
    Safe_Release(m_pGameInstance);
    Safe_Release(m_pDeviceContext);
    Safe_Release(m_pDevice);
}
```

오브젝트의 기본 `Update`가 맵을 돌며 스크립트를 모두 갱신합니다(<FigRef n={3} />). 파생 오브젝트가 `Super::Update`만 부르면 붙어 있는 스크립트가 함께 갱신되므로, 카타나 제로 모작처럼 컴포넌트마다 갱신 호출을 적지 않아도 됩니다. 해제도 오브젝트가 사라질 때 슬롯 배열과 맵을 차례로 비워 한 번에 끝납니다.

## 5. 피드백

**스크립트 컴포넌트를 조회할 때 캐스팅 문제가 다시 생겼습니다.** `Get_Script_Component`는 `CMonoBehaviour*`를 돌려주므로, 상태 코드마다 `static_cast<CStatComponent*>(Get_OwnerObject()->Get_Script_Component(L"StatComponent"))`처럼 이름 문자열과 캐스팅을 함께 적습니다. 이름에 오타가 있어도 컴파일은 되고, 실행 중에 `nullptr`을 역참조합니다. `Get_Script_Component<CStatComponent>()`처럼 타입을 받아 `dynamic_cast`까지 하는 템플릿을 두거나, 이름 상수를 한곳에 모았어야 합니다.

남은 개선점입니다.

- 스크립트는 기본 `Update`가 모아 갱신하지만 슬롯의 상태 컴포넌트는 `CPlayer::Update`가 직접 부릅니다. 새 컴포넌트를 붙일 때마다 갱신 위치를 따로 확인해야 합니다.
- `Get_Component` 등의 범위 검사(`T::_ID >= TRANSFORM || T::_ID < END`)는 항상 참입니다. `&&`여야 잘못된 `_ID`를 컴파일 단계에서 막을 수 있습니다.
- `Remove_Script_Component`는 맵에서 지우기만 하고 해제하지 않아, 호출하면 컴포넌트가 남습니다(아직 사용처는 없음).
