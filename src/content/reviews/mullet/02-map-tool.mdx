## 1. 개요

<Chips items={frontmatter.chips} />

데이터 주도 설계는 맵 배치처럼 자주 바뀌는 내용을 코드 밖 데이터 파일로 빼고, 게임이 그 데이터를 읽어 객체를 만들게 하는 방식입니다. 생성 쪽은 보통 팩토리에 (종류 → 생성 함수)를 등록해 두어, 종류가 늘어도 로더는 손대지 않습니다.

등록 테이블 덕분에 새 오브젝트를 추가해도 로더와 팩토리 코드는 그대로이고 등록 한 줄만 늘어납니다. 맵은 빌드 없이 데이터 파일만 고쳐 수정할 수 있습니다.

## 2. 문제

> 3D 스테이지마다 벽·바닥·경사·타일·몬스터를 수백 개씩 배치해야 했습니다. 좌표를 코드에 직접 적으면 고칠 때마다 빌드해야 하고, 팀원들이 같은 방식으로 맵을 만들 수도 없습니다. 오브젝트 종류도 계속 늘어나는데, 로더가 `switch`로 종류를 나누면 종류가 추가될 때마다 로더를 고쳐야 합니다. 도로 스테이지는 도로가 끝없이 이어져야 했습니다.

## 3. 구조 요약

저장·보관·생성을 나눴습니다. 파일 관리자는 JSON과 구조체 사이만 오가고, 그 데이터로 무엇을 만들지는 팩토리에 등록된 생성 함수가 정합니다. 그래서 로더와 스테이지는 오브젝트 종류를 모릅니다.

에디터에 배치한 객체는 저장할 때 각자 가상 함수 `ExportData`로 카테고리·타입·버퍼·텍스처·행렬을 채우고, `ExportObjectData`가 레이어를 돌며 이를 모읍니다. 저장 코드는 객체 종류를 모릅니다. 배치할 때는 `CDummyTile::PosUpdate()`가 피킹 위치에 미리보기 타일을 띄웁니다.

```cpp
std::vector<MAPOBJECTDATA> CObjectManager::ExportObjectData(_uint iSceneID, const _tchar *pLayerTag)
{
	list<CGameObject *> *pList = Get_ObjectList(iSceneID, pLayerTag);
	if (!pList || (*pList).size() <= 0)
		return {};

	std::vector<MAPOBJECTDATA> returnData;
	returnData.reserve((*pList).size());

	for (CGameObject *element : (*pList))
	{
		MAPOBJECTDATA pSrc;
		element->ExportData(&pSrc);
		returnData.push_back(pSrc);
	}

	return returnData;
}
```

파일 관리자는 구조체와 JSON 사이의 변환(`to_json`·`from_json`)과 파일 경로만 맡고, 데이터로 무엇을 만들지는 모릅니다. `SaveDataFile`은 레이어 데이터를 JSON 배열로 저장하고, `LoadDataFile`은 읽은 데이터를 `CDataManager`에 레이어별로 넣어 둡니다. 프리팹 정의는 `Save/LoadPrefabDataFile`이 따로 다룹니다.

#### A. 구조체 직렬화

```cpp
void to_json(json &_j, const MAPOBJECTDATA &_tData)
{
    _j = json
    {
        {"ObjectCategory", _tData.eCategory},
        {"ObjectType", _tData.iType},
        {"Color", _tData.dwColor},
        {"TransformData", _tData.transform},
        {"TextureData", _tData.texture},
        {"PanelData", _tData.panelBuffer}
    };
}

void from_json(const json &_j, MAPOBJECTDATA &_tData)
{
    _j.at("ObjectCategory").get_to(_tData.eCategory);
    _j.at("ObjectType").get_to(_tData.iType);
    _j.at("Color").get_to(_tData.dwColor);
    _j.at("TransformData").get_to(_tData.transform);
    _j.at("TextureData").get_to(_tData.texture);
    _j.at("PanelData").get_to(_tData.panelBuffer);
}
```

</Editor>

구조체마다 `to_json` / `from_json`을 정의해 두면 nlohmann/json이 트랜스폼·텍스처·패널 크기 같은 중첩 구조체까지 알아서 변환합니다. 사람이 읽을 수 있는 형식이어서, 저장·로드 버그는 파일을 열어 바로 확인할 수 있었습니다.

```cpp
HRESULT CFileManager::SaveDataFile(_uint iSceneID, const _tchar *szLayerTag)
{
    std::vector<MAPOBJECTDATA> objectDatas = CObjectManager::GetInstance()->ExportObjectData(iSceneID, szLayerTag);
    // ... 코드 중략
    json jArray = json::array();
    for (const auto &data : objectDatas)
    {
        jArray.push_back(data);
    }

    // " / " 연산자 오버로딩을 통해서 파일 경로 만들기
    filesystem::path dir = GameDataPath / SceneIdToWstring(iSceneID) / szLayerTag / L"data.json";
    if (!dir.parent_path().empty())
    {
        filesystem::create_directories(dir.parent_path());
    }
    // ... 코드 중략
    // setw(i) 출력될 값의 최소폭을 i 만큼 지정
    // Json 이므로 4칸 들여쓰기로 출력
    ofs << std::setw(4) << jArray << std::endl;
    ofs.close();

    return S_OK;
}
// ... 코드 중략

HRESULT CFileManager::LoadDataFile(_uint iSceneID, const _tchar *szLayerTag)
{
    filesystem::path dir = GameDataPath / SceneIdToWstring(iSceneID) / szLayerTag / L"data.json";
    // ... 코드 중략
    std::ifstream ifs(dir, std::ios::in | std::ios::binary);
    if (!ifs.is_open())
    {
        return E_FAIL;
    }

    json jArray;
    ifs >> jArray;

    for (const auto &jObj : jArray)
    {
        MAPOBJECTDATA objData = jObj.get<MAPOBJECTDATA>();
        CDataManager::GetInstance()->AddData(szLayerTag, objData);
    }

    ifs.close();
    return S_OK;
}
```

</Editor>

경로는 `std::filesystem::path`의 `/` 연산자로 씬과 레이어 이름을 이어 만들고, 없는 폴더는 저장할 때 만듭니다. 읽은 데이터는 바로 객체로 만들지 않고 `CDataManager`에 레이어별로 넣어 두므로, 언제 생성할지는 스테이지가 정합니다.

```cpp
CGameObject *CMapFactory::Create(ObjectCategory _eCategory, _uint _iType, void *_pData)
{
	// ... 코드 중략
	_uint iCategory = static_cast<_uint>(_eCategory);
	auto itr = m_Register[iCategory].find(_iType);
	if (itr == m_Register[iCategory].end())
	{
		MSG_BOX("CMapFactory::Create, std::function is invalid");
		return nullptr;
	}

	return (*itr).second(_pData);
}
```

`switch` 대신 등록 테이블을 쓰므로 새 오브젝트를 추가해도 로더와 팩토리 코드는 그대로이고, 등록 한 줄만 늘어납니다(<FigRef n={3} />). 로더는 (카테고리, 타입)으로 함수를 찾기만 합니다. 생성 함수는 `void*` 데이터를 받고, 각 객체가 그것을 자기 데이터로 해석합니다.

## 5. 피드백

**팩토리에서 없앤 분기가 파일 관리자로 옮겨 왔습니다.** 맵 오브젝트, 프리팹, 배치된 프리팹마다 `Save...` / `Load...` 함수 쌍이 따로 있어서, 데이터 종류가 늘 때마다 `CFileManager`에 함수가 늘어납니다. 데이터 종류별 직렬화를 각 데이터 클래스에 맡겼다면 파일 관리자는 바뀌지 않았을 것입니다.

남은 개선점입니다.

- 열거형 직렬화 매크로를 다른 네임스페이스에 선언해, 파일에 `"ObjectCategory": 3`처럼 숫자로 저장됩니다. 사람이 읽고 고치기 쉬운 JSON이라는 의도는 절반만 이뤘습니다.
- `ifs >> jArray`는 JSON이 깨져 있으면 예외를 던지는데 받는 곳이 없어, 파일 하나만 잘못돼도 게임이 종료됩니다.
- 읽은 데이터가 객체를 만든 뒤에도 다음 씬 로드까지 `CDataManager`에 남습니다. 생성이 끝나면 비워야 합니다.
- 스테이지마다 `SetData` / `InstancingObjects`를 복사해 쓰고, 도로 구간은 재사용하면서도 구간을 옮길 때마다 드론 9마리는 `Clone_GameObject`로 새로 만듭니다. 공통 로딩 단계로 묶고 몬스터도 풀로 돌리는 편이 일관됩니다.
