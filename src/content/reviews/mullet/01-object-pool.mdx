## 1. 개요

<Chips items={frontmatter.chips} />

오브젝트 풀은 생명주기가 짧은 객체를 매번 `new`/`delete` 하지 않고, 씬이 시작될 때 미리 만들어 두었다가 스폰과 회수로 돌려 쓰는 방식입니다. 플레이 중에는 할당과 해제가 일어나지 않고, 스폰과 회수 모두 탐색 없이 O(1)에 끝납니다.

풀 클래스에는 타입별 코드가 하나도 없습니다. 어떤 `CGameObject` 파생 타입이든 같은 풀에 담을 수 있고, 새 풀은 enum 한 줄과 `Ready_Pools` 한 줄로 추가됩니다.

## 2. 문제

> 총알·미사일·피격 이펙트처럼 한 프레임에 수십 개씩 생겼다가 금방 사라지는 객체가 많았습니다. 매번 생성하고 해제하면 비용이 크고, 팀원마다 자기가 만든 객체를 제각각 관리하게 됩니다. 카타나 제로 모작의 풀은 타입마다 템플릿 인스턴스여서 풀 하나를 늘릴 때마다 세 곳을 고쳐야 했습니다. 이번에는 **어떤 `CGameObject` 파생 타입이든 같은 풀 클래스에 담을 수 있어야** 했습니다.

## 3. 구조 요약

풀의 중심은 객체 배열 하나와 활성·대기를 가르는 경계 하나입니다. 스폰은 경계를 한 칸 늘리고, 회수는 회수할 객체를 마지막 활성 객체와 맞바꾼 뒤 경계를 한 칸 줄입니다. 어느 쪽도 탐색이나 메모리 할당이 없습니다.

### 책임 분리

<div class="tbl">

| 클래스 | 책임 |
| --- | --- |
| `CObjectPoolManager` | 풀 종류별 생성, 활성 객체 갱신, `DEAD` 반환 시 회수 |
| `CObjectPool` | 미리 복제한 객체의 활성·대기 경계 관리 |
| `CGameObject` 파생 | 스폰 데이터로 자기 초기화, 회수 시 정리 |
| 호출부 | 풀 종류 + 스폰 데이터 + 위치 지정 콜백 전달 |

</div>

## 4. 코드 리뷰

호출부는 `CObjectPoolManager::Spawn` 한 줄에 풀 종류와 스폰 데이터, 필요하면 위치 콜백만 넘깁니다. 객체를 만들고 지우는 일이나 개수 관리는 신경 쓰지 않습니다.

#### A. 플레이어 총알

이 코드는 팀원이 작성했습니다. 총알은 위치와 방향이 `BulletData` 안에 들어 있어 콜백 없이 데이터만 넘깁니다. 발사 위치·방향·속도·소유자를 채워 넘기면 나머지는 `CBullet::Spawn_Pooling`이 처리합니다.

<Tab>

관리자는 `PoolType` enum을 인덱스로 쓰는 `m_arrayPools`에 풀을 모아 두고, 풀 객체의 갱신과 회수를 대신 맡습니다. 호출부가 쓰는 입구는 `Spawn` 하나뿐입니다. 풀은 씬이 시작될 때 `Ready_Pools()`에서 만들고, 씬을 정리할 때 `All_Despawn()`으로 비웁니다.

#### B. 갱신과 자동 회수

<Editor file="CObjectPoolManager.cpp" fn="CObjectPoolManager::Update(...)">

```cpp
void CObjectPoolManager::Update(const _float _fDeltaTime)
{
	for (CObjectPool *pElement : m_arrayPools)
	{
		if (pElement)
		{
			for (int i = pElement->Get_ActiveCount() - 1; i >= 0; --i)
			{
				CGameObject *pGo = pElement->Get_ActiveAt(i);
				int iEvent = pGo->Update_GameObject(_fDeltaTime);
				if (iEvent == DEAD)
				{
					pElement->Despawn(pGo);
				}
			}
		}
	}
}
```

</Editor>

풀 객체는 레이어에 넣지 않고 관리자가 직접 갱신합니다. 객체는 수명이 끝나면 `DEAD`만 반환하고, 회수 호출은 관리자가 합니다.

순회를 **역순**으로 한 데는 이유가 있습니다. `i`번째를 회수하면 마지막 활성 객체가 `i` 자리로 옮겨 오는데, 그 객체는 인덱스가 더 크므로 이번 프레임에 이미 갱신을 마친 상태입니다. 정순으로 돌면 옮겨 온 객체를 건너뛰게 됩니다.

</Tab>
<Tab>

풀은 프로토타입 복제본 배열 `m_Objects`와 정수 `m_iActiveCount` 하나로 무엇이 사용 중인지 표현합니다. 앞쪽 `[0, m_iActiveCount)`가 활성, 뒤쪽이 대기 구간이고, `m_iActiveCount`는 활성 개수이면서 다음에 스폰할 인덱스입니다.

#### A. 생성

<Editor file="CObjectPool.cpp" fn="CObjectPool::Create(...), CObjectPool::Ready_ObjectPool(...)">

```cpp
CObjectPool *CObjectPool::Create(const wstring &_pPrototypeTag, _uint _iReserve)
{
	CObjectPool *pInstance = new CObjectPool(_iReserve);
	if (FAILED(pInstance->Ready_ObjectPool(_pPrototypeTag)))
	{
		Safe_Release(pInstance);
		return nullptr;
	}
	return pInstance;
}

HRESULT CObjectPool::Ready_ObjectPool(const wstring &_pPrototypeTag)
{
	CGameObject *pPrototype = CObjectManager::GetInstance()->Find_Prototype(_pPrototypeTag.c_str());
	if (!pPrototype)
	{
		return E_FAIL;
	}
	for (int i = 0; i < m_Objects.capacity(); ++i)
	{
		CGameObject *pGo = pPrototype->Clone();
		if (!pGo)
		{
			return E_FAIL;
		}
		m_Objects.push_back(pGo);
	}

	m_PrototypeTag = _pPrototypeTag;

	return S_OK;
}
```

</Editor>

생성자에서 `reserve`로 자리를 잡아 두고, `Ready_ObjectPool`이 그 수만큼 복제본을 채웁니다. 엔진의 프로토타입 시스템을 그대로 활용했습니다. 원본은 로딩 때 리소스까지 준비되어 있어 풀은 `Clone()`만 부르면 되고, 그래서 풀 클래스에 타입별 코드가 하나도 없습니다.

#### B. 스폰

<Editor file="CObjectPool.cpp" fn="CObjectPool::Spawn(...)">

```cpp
CGameObject *CObjectPool::Spawn(void *pArg, std::function<void(CGameObject *)> _callback)
{
	if (m_iActiveCount >= m_Objects.size())
	{
		return nullptr;
	}
	CGameObject *pGo = m_Objects[m_iActiveCount];
	if (pArg) pGo->Spawn_Pooling(pArg);
	else pGo->Spawn_Pooling();
	pGo->Set_ActiveIndex(m_iActiveCount);
	if (_callback) _callback(pGo);
	++m_iActiveCount;
	return pGo;
}
```

</Editor>

스폰할 객체는 항상 `m_Objects[m_iActiveCount]`이므로 찾을 필요가 없습니다. 초기화는 두 단계로 나눴습니다.

- `Spawn_Pooling(pArg)`: **타입이 아는 값**(총알 속도, 이펙트 옵션)으로 객체가 스스로 초기화
- `callback(pGo)`: **호출부만 아는 값**(생성 위치 등)을 그 자리에서 설정

자기 활성 번호를 `Set_ActiveIndex`로 기록해 두는 것은 회수할 때 쓰기 위해서입니다.

#### C. 회수

<Editor file="CObjectPool.cpp" fn="CObjectPool::Despawn(...)">

```cpp
HRESULT CObjectPool::Despawn(CGameObject *_pObject)
{
	// ... 코드 중략
	int iNeed_Despawned_Index = _pObject->Get_ActiveIndex();
	if (iNeed_Despawned_Index < 0 || iNeed_Despawned_Index >= m_iActiveCount)
	{
		return E_FAIL;
	}

	int iLastActiveIndex = m_iActiveCount - 1;
	if (iNeed_Despawned_Index != iLastActiveIndex)
	{
		std::swap(m_Objects[iNeed_Despawned_Index], m_Objects[iLastActiveIndex]);

		const int &Swaped_Despawned_Index = iNeed_Despawned_Index;
		const int &Swaped_iLastActiveIndex = iLastActiveIndex;

		m_Objects[Swaped_Despawned_Index]->Set_ActiveIndex(Swaped_Despawned_Index);
		m_Objects[Swaped_iLastActiveIndex]->Set_ActiveIndex(Swaped_iLastActiveIndex);
	}

	if (FAILED(_pObject->Despawn_Pooling()))
	{
		return E_FAIL;
	}

	--m_iActiveCount;

	return S_OK;
}
```

</Editor>

회수할 객체의 위치는 `m_iActiveIndex`로 바로 알 수 있습니다. 그 자리를 마지막 활성 객체로 채우고 경계를 줄이면 활성 구간에 빈칸이 생기지 않습니다. 자리가 바뀐 두 객체의 활성 번호는 그 자리에서 고쳐 둡니다. 순서는 보존되지 않지만 풀 객체끼리는 순서에 의미가 없어 문제가 되지 않습니다.

</Tab>
<Tab>

풀이 타입을 몰라도 되는 것은 객체 쪽에 둔 활성 번호 `m_iActiveIndex` 하나와 가상 함수 세 개 덕분입니다. 풀을 만들 때는 `Clone()`으로 복제본을 만들고, 스폰할 때는 `Spawn_Pooling(pArg)`이 인자를 자기 데이터로 해석해 초기화하며, 회수할 때는 `Despawn_Pooling()`이 뒷정리를 합니다.

풀링 대상 타입은 모두 `Spawn_Pooling(pArg)`에서 자기 데이터를 받아 초기화합니다.

<div class="tbl">

| 클래스 | pArg로 받는 데이터 | 회수 시 정리 |
| --- | --- | --- |
| `CEffect_Pixel` | `EffectOptions` | 파티클 목록·옵션 |
| `CEffect_Pixel_Sprite` | `SpriteParticleOptions` | 파티클 목록·프레임 |
| `CEffect_World` | `EFFECTINFO` | 회전·크기·프레임 |
| `CBullet` | `BulletData` | 수명·크기 |
| `CMissile` | `MissileData` | 연결된 경고 원, 비행 상태 |
| `CWarningCircle` | 없음 (반지름·바닥 위치 초기화) | 경과 시간 |

</div>

#### A. 타입별 훅 — 총알

<Editor file="CBullet.cpp" fn="CBullet::Spawn_Pooling(...), CBullet::Despawn_Pooling(...)">

```cpp

{

        return E_FAIL;

    if (m_pTextureCom)
        m_pTextureCom->Set_Zero_Frame();

    if (BulletData *pData = reinterpret_cast<BulletData *>(pArg))

        TransformInfo.fSpeed = pData->fSpeed;
        TransformInfo.fRotationSpeed = 0.f;

        m_fSpeed = pData->fSpeed;
        Fire(pData->vMuzzlePosition, pData->vLookDir);

        // owner 적용
        m_eOwner = pData->eOwner;
    }
    else
    {
        MSG_BOX("CBullet::Spawn_Pooling, no data");
        return E_FAIL;
    }


    return S_OK;
}

HRESULT CBullet::Despawn_Pooling()
{
    if (FAILED(CGameObject::Despawn_Pooling()))
```

스폰 인자는 `void*` 하나로 통일하고, 받는 쪽이 자기 타입으로 해석합니다. 총알은 `BulletData`로 속도·방향·소유자를 정하고, 회수될 때 수명과 크기를 되돌립니다. 이펙트와 미사일도 같은 방식으로 자기 데이터만 다루므로, 타입이 늘어도 풀 코드는 바뀌지 않습니다.

## 5. 피드백

**풀을 추가하려면 여전히 엔진 코드를 고쳐야 했습니다.** `PoolType` enum은 엔진 헤더에 있고, `L"Prototype_GameObject_Bullet"` 같은 클라이언트 프로토타입 태그가 엔진의 `Ready_Pools`에 들어 있습니다. 엔진이 클라이언트 객체의 이름을 아는 구조라, 팀원이 새 객체를 풀링하려면 엔진을 건드려야 했습니다. 풀 종류와 프로토타입 태그를 엔진 밖으로 빼고, 클라이언트가 직접 등록하게 했어야 합니다.

남은 개선점입니다.

- 풀이 가득 차면 알림 없이 `nullptr`를 반환해서 풀 크기를 감으로 정했습니다. 최대 사용량을 기록하거나 부족할 때 로그를 남겨 근거를 만들어야 합니다.
- `CObjectPoolManager::Spawn`은 풀 생성이 실패했을 때(프로토타입 태그 오타 등) 빈 슬롯을 그대로 역참조합니다. 등록 시점에 실패를 바로 알려야 합니다.
- `Ready_Pools`는 시작하자마자 `All_Clear()`로 배열을 비우므로, 이어지는 `if (!m_arrayPools[...])` 검사는 항상 참입니다. 의미 없는 분기는 정리해야 합니다.
