GameplayTag을 매핑하여 해당 Tag에 맞는 Layout을 띄울수 있게 기반을 만들어봤다. 그렇다면 해당 Layout안에 또다른 UI Widget이 추가될건데(Ex. 상점, 아이템창 등) 그러한 구분은 또 어떻게 이루어질까?
이때까지 만든 구조는 하나뿐인 큰 PrimaryLayout에 상황에 맞는 4가지의 Layout을 만들었다. 해당 4가지의 Layout안에 또다른 UI들을 UIExtension으로 구분한다. 이것또한 GameplayTag로 구분이 이루어지는데, 첫번째 접근에 어떤 Layout인지? 두번째 접근에 그 Layout내에서 어떤 UIExtension인지? 정리하자면 PrimaryLayout( Layout( UIExtension ) )으로 존재한다고 보면된다.

PrimaryLayout은 무조건 기본적으로 생성되어있는것이고, 해당 Layout은 어느 시점에 생성하고 관리할지 등은 GameFeatureAction을 이용하게 된다. 해당 액션이 발동하면 Layout이 장착되고 거기에 해당되는 UIExtension도 장착아 이루어지게 한다는것이다.

GameFeatureAction의 경우 UEngine을 Subsystem에서 상속받아 사용되고 있기 때문에, 관리가 Instance별로 되지 않는다. 그래서 굳이 World단위로 캐싱해서 진행했었다. 결론적으로 PIE 환경을 여러개를 켜서 사용해도 FPerContextData로 월드별 데이터가 정리될것이기 때문에 이러한 경우를 대비해서 꼭 사용되고 있는것이다.

ComponentRequestHandle의 경우 진행하면서 이해하는게 빠르고, Layout이 생성되서 관리 될텐데 그 부분을 캐싱해두는곳이 LayoutsAdded 이다. UIExtensionHandle은 FBJHUDElementEntry를 위한 Handle이다. 즉 FBJHUDElementEntry를 한번더 가공해서 Handle 형태로 들고있는 것이다.

PerContextData는어떤 Layout인지 Widget을 사용할지에 대한 정보가 담겨있다. Layout을 순회하는 로직이긴 하지만 보통 한개이다. LayoutClass를 가져와서 해당 태그와 함께 LocalPlayer에게 넘겨주고있다.

즉, PrimaryLayer에게 이 Tag(LayerID)에 해당하는 Layout(ConcreteWidgetClass)을 넣어줘라!를 요청하는것이다. 요청과 동시에 ActiveData의 LayoutsAdded에 업데이트해준다. 신기하게 요청은 CommonUIExtension에서 진행한다.

그다음이 중요한데 Widget(Layout)을 ExtensionSubsystem을 통해 RegisterExtensionAsWidgetForContext하는데, 함수 이름에서 봐서 알수 있듯이 실제로 추가해서 등록하는게 아닌, 관리할 수있도록 Subsystem에 등록하는것이다.

이어서 RegisterExtensionAsWidgetForContext를 마저 구현해보자. ExtensionMap의 경우 하나의 GaemplayTag에 여러개의 Extension이 존재할수있으니 Array로 관리하게되며 해당 Array를 Value값을 지정해주었다.

Tag로 Map에 추가와 동시에 List추출, UIExtension은 SharedPtr이니 MakeShare!하며 List에 추가하며 데이터를 넣어준다.

Lyra의 InGameLayer는 어떻게 구성되는지 보며 정리해보자. 이 Layout을 부르는건 PrimaryLaout 가장 큰틀이라고 보면되고 해당 Widget들을 포함하는 하나의 테마가 Layout이다. 중간에 작은 글씨들이 보이는데 GameplayTag이다. 해당 태그 위치에 Widget(UIExtension)들이 장착되는것이다. 현재 UIExtension은 등록까지만 진행되었으니 앞으로 장착이 어떻게 이루어지는지 구현해볼예정이다.
